# Step 1 — Frozen objectives

## Status

Frozen as of repository initialisation. Changing these requires a corresponding
revision of `docs/03-architecture.md`, because the architecture is derived from them.

## Objective 3

> To develop a multi-evidence trust mechanism for verifying malicious beacon nodes
> using behavioural and localization consistency.

**Operational reading.** Given a *candidate* malicious beacon node emitted by Paper 1,
compute a confidence score from at least two mutually independent evidence classes
and return a verdict in `{normal, suspicious, confirmed-malicious}`.

The word doing the work here is **verifying**. Paper 1 detects; Paper 2 verifies.
A verification mechanism is allowed to overturn Paper 1's candidacy — that is the
point of it, and the false-positive reduction it buys is a claimable result.

**Independence requirement.** The two evidence classes must be able to disagree.
Behavioural evidence (forwarding ratio, drop ratio, delay) is generated by the
routing plane. Localization evidence (RSSI-derived distance vs. claimed position,
neighbour agreement) is generated by the physical/localization plane. A node can
lie about position while forwarding perfectly, or forward badly while reporting
position honestly. If a proposed feature cannot produce that disagreement, it does
not count as a second evidence class.

## Objective 4

> To isolate confirmed malicious beacon nodes and dynamically recover secure routes
> while minimizing the impact on network performance.

**Operational reading.** On a `confirmed-malicious` verdict: blacklist the node,
purge it from routing state, propagate the verdict, trigger route rediscovery under
an exclusion constraint, and measure how much of the pre-attack network performance
is restored and how quickly.

The clause *"while minimizing the impact on network performance"* is an explicit
cost constraint, so isolation overhead is a first-class measured quantity, not a
footnote. Two mechanisms that both isolate correctly are separated by their control
overhead and recovery latency.

## Distinction from the closest prior work

The literature file identifies **EMBN-MANET** as the nearest existing work; it already
addresses malicious-beacon elimination. Trust-based routing, trust-change detection
and verification approaches also exist independently in the surveyed set.

The contribution claimed here is therefore **not**:

- another weighted trust formula, nor
- beacon elimination as such.

It is the **fusion of behavioural and beacon/localization evidence into a single
verification decision, with a three-way verdict and a measured recovery path.**
The claim stands or falls on the ablation in Step 12: the fused detector must beat
each single-evidence detector, and the recovery stage must show measurable network
restoration beyond removal alone.

## Non-objectives

Deliberately out of scope, to keep the first implementation defensible:

- Cryptographic beacon authentication (orthogonal, and would mask the trust signal).
- Colluding multi-beacon attacks (see `docs/02-attack-model.md`, deferred).
- Energy-optimal monitoring scheduling.
